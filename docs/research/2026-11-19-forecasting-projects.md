# 自动取证与二元事件预测：现有项目调研

调研日期：2026-11-19。范围是“用户一句话 → 系统规范问题 → 自动研究 → 更新二元概率 → 持续跟踪”，仅查阅官方代码、文档和作者论文。本次没有安装、复制或运行外部项目，没有调用付费模型或搜索 API；下列适配方案是建议，不代表应用已经接通。

## 1 可以借什么，不能误认为什么

| 对象 | 核实的能力与许可证 | 对本项目的适配结论 |
| --- | --- | --- |
| Metaculus forecasting-tools | Python 研究与预测工具库；研究、重复预测、聚合、报告及平台 API；MIT | 最接近预测输出管线。借鉴问题契约、报告结构及研究／预测分离；不直接替换 Node Harness |
| ForecastBench | 自动生成未来问题、收集结果和评估预测的基准管线；MIT 代码 | 借评估设计和题目／结算记录；不是自主多 Agent 执行框架 |
| FutureSearch Python SDK | 面向远程预测／研究服务的客户端，支持二元概率与理由；SDK 为 MIT | 产品交互值得参考；公开客户端不能替代本项目自己的执行器和 Agent 设计 |
| BLF v5 论文 | 带结构化信念状态的搜索型预测 Agent；论文 CC BY 4.0，本次未核实到其公开实现 | 借“概率＋支持／反对证据＋未决问题”的状态设计；不作为可安装依赖 |

许可证核实：[Metaculus MIT](https://github.com/Metaculus/forecasting-tools/blob/main/LICENSE)、[ForecastBench MIT](https://github.com/forecastingresearch/forecastbench/blob/main/LICENSE)、[FutureSearch SDK MIT](https://github.com/futuresearch/futuresearch-python/blob/main/LICENSE.txt)、[BLF 论文与许可](https://arxiv.org/html/2604.18576v5)。如后续复制或实质改编 MIT 代码，应保留原版权与许可声明，并锁定实际使用的提交；本次只是评估。

## 2 核实结果与采用边界

### 2.1 Metaculus forecasting-tools：优先参考预测管线

官方 `ForecastBot` 将研究与预测分开，可配置每道问题的研究次数、每份研究的预测次数，再汇总为报告。其 `Notepad` 可保存同一问题跨预测的组织性记录。当前二元报告的默认聚合代码使用中位数，不是投票开会，也不是加总新闻分数。[基类源码](https://github.com/Metaculus/forecasting-tools/blob/main/forecasting_tools/forecast_bots/forecast_bot.py)、[二元报告源码](https://github.com/Metaculus/forecasting-tools/blob/main/forecasting_tools/data_models/binary_report.py)。

其 2026 Fall 模板明确区分 `run_research` 与二元预测；研究策略包含 AskNews 和 SmartSearcher 等分支。二元提示要求考虑剩余时间、现状及 Yes／No 场景。官方 README 说明相关网络检索需要对应服务的 API key。因此拿到 Python 包并不等于免费获得全网搜索，也不等于已经建立独立多 Agent 通信。[模板源码](https://github.com/Metaculus/forecasting-tools/blob/main/forecasting_tools/forecast_bots/official_bots/template_bot_2026_fall.py)、[项目 README](https://github.com/Metaculus/forecasting-tools)。

本项目建议：用现有 Node／SQLite 实现同等职责边界：`ResearchReport` 提供来源，`ForecastCandidate` 提供对同一问题的概率，确定性聚合处理器保存最终版本。若将来需要其平台客户端或实验工具，可通过独立 Python 进程及 JSON 协议桥接；先确认它比直接实现小模块省事，再引入额外运行环境。不要把其完整 Streamlit 前端接入像素界面。

### 2.2 ForecastBench：用来检验效果，不能用来填补执行功能

官方文档描述了问题生成、数据核验、结果处理和评分管线；网站区分基于同一观测条件提出的多个预测期限。它持续使用提交时尚无答案的未来问题，避免单纯历史问答带来的已知答案污染。其部署说明涉及 Python 与 Google Cloud Functions，本项目不需要为小型课程实验复制整个云部署。[官方文档](https://www.forecastbench.org/docs/)、[期限说明](https://www.forecastbench.org/about/)、[代码与部署说明](https://github.com/forecastingresearch/forecastbench)。

本项目建议：先建立自己的小型前瞻题集，记录题目版本、预测时间、目标时间、当时材料快照、真实结果和错误原因。比较“基准率／市场参考”“一个研究员”“多研究员直接聚合”“加入争议补查”，保持同题、同截点、同模型与相近预算。基准不替我们实现 Supervisor、来源抓取或持续监听。

### 2.3 FutureSearch：交互形态接近，但 SDK 不是可拆下的预测引擎

公开 SDK 可用一句问题调用 `forecast(..., forecast_type="binary")`，返回概率及理由，也公开了并行研究操作的客户端入口；README 明确要求 API key，并链接费用说明。本次核实的公开仓库是 SDK，不能据此说已经取得其服务端模型编排或核心研究实现。[官方 SDK](https://github.com/futuresearch/futuresearch-python)。

本项目建议：参考“先问问题，再由服务进行研究”的用户流程及“概率＋理由”结果格式。课程主路径继续使用自己的分工、工具账本、通信和恢复。未来若把外部预测服务作为工具，应显式标为外部参考，并与自己的预测、市场报价分列；不能让一个远程答案替代全部多 Agent 工作。

### 2.4 BLF：有价值的是信念状态，而非给新闻硬贴一个涨跌分

作者的 v5 将系统描述为搜索型 ReAct Agent：循环选择搜索、阅读、特定数据工具或提交，持有包含概率、支持／反对证据及未决问题的结构化状态。作者称其更新为 Bayesian-inspired，不能直接视为精确贝叶斯推断；论文还讨论了聚合与校准的评估局限，并表示代码与数据将来发布。[BLF v5](https://arxiv.org/html/2604.18576v5)。

本项目建议：为每个问题保存紧凑 `BeliefState`，将尚未解决的事实问题交给下一轮调查。它可以与带来源的关系图连接；不必先做一个庞大“世界模拟器”才能提供有用结果。论文的比较结果不代表本项目已经有相同预测准确率。

## 3 概率时间曲线必须分清的三个对象

以下是本项目建议，尚未实现。

### 固定目标的判断更新

一题固定目标时间 `T`，每次在新的观察时间 `t` 预测同一个结果：`p(t,T) = P(Y_T = Yes | 当时可见信息)`。曲线横轴为我们实际发布判断的时间，纵轴为 `probabilityYes`。今天读到一篇昨天的新闻，只能给今天的预测新增依据，不能伪造成昨天已发布过的判断。

例如“在周五结束时，甲是否仍担任公司 CEO”：周一、周二、周三对这个同一周五目标的概率可以依次更新。各点必须带题目版本、实际发布时间、材料快照和变更原因。

### 当前看到的多个未来期限

同一观察时刻 `t`，对 24 小时、48 小时、7 天分别预测，是 `p(t,T1)`、`p(t,T2)`、`p(t,T3)` 三个不同目标，而不是把一条历史概率曲线向右延长。前端可用期限按钮切换相应曲线，另显示多个期限的当前点。

若命题是“在期限前至少发生一次”，延长窗口时其真实累计发生概率应不减；若命题是“在某时点仍在任”，不能一概套用累计发生概率的单调规则。价格上涨也不是累计首次发生事件，必须先明确比较口径。

### 持续关注的滚动任务

“每天都预测未来 48 小时”意味着目标时间每天移动。应由一个长期主题生成按日期固定的窗口实例，或至少保存清晰的目标时间与窗口编号。可以显示“滚动 48 小时预测”的序列，但必须告知用户各点预测的是不同目标，不能与固定到期题的历史判断混成一条无说明曲线。

因此，不建议首版用过去几个概率点做线性外推来预测未来概率：过去点是系统在不同信息条件下的判断，不是世界状态的独立数值样本。未来目标须重新使用当前证据、基准率、条件路径及必要的数据模型进行估计。

## 4 概率如何产生，怎样避免数字看起来很科学

以下为推荐的首版设计，须通过本项目实验验证。

1. **先定可结算问题。** 预设模式可给 48 小时窗口、默认时区和默认来源规则，但“涨”仍须落到可复核口径，例如指定交易所、比较基准与目标常规交易时段收盘价。非交易日要查交易日历，不能简单把 48 小时当两个交易日。严格模式只是展开这些系统预填字段。
2. **读取基准，不从新闻情绪直接计算概率。** 对低频事件需要适用的历史基准率；市场合约可作另一条参考，但须对齐对象、期限、结算规则与报价时点。没有合适基准时标记缺失，不凭空填“行业经验 90%”。
3. **首次判断独立。** 按需选择两到三位不同调查方法的研究员，先给独立报告和估计，暂不互看概率。之后比较具体事实冲突，由核验研究员补查。角色数量或一致人数不是校准后的可信度。
4. **去重后更新信念。** 新资料经过正文哈希、规范 URL、事件实体与主张聚类，记录原始出处。十个网站转发同一公告只算一组来源；若转载加入新的独立事实，可作为另一条主张核验，而不是简单整篇删除。旧材料反复阅读不能反复提高概率。
5. **保留简单聚合基线。** 初版比较中位数或均值，再比较主 Agent 裁决。分工研究员共享资料、同用一个模型，不能假设其数值统计独立；不能直接把各自胜算连乘。模型估计的似然比也仍是主观估计，用 log-odds 更新不会自动变成精确统计模型。
6. **单独做概率校准。** 有足够已结算样本后，才训练 Platt 等校准器，并按事件分组、按时间前后切分验证。同一事件不同日期或不同期限的记录不能跨训练／测试泄漏。不能在本题结果已经知道后校准，再声称是当时可用的概率。
7. **结果卡表达同一个量。** 主数值始终是“发生 Yes 的概率”，例如 35%；倾向答案为“否”，否的概率则为 65%。答案、资料充分程度、团队分歧、服务是否故障应分别显示。未取得可用资料时可以不发布概率，不能用 0% 或伪装成 50% 的成功预测代替错误状态。
8. **用结果评价。** 二元 Brier 为 `(p-y)^2`，在本项目约定下越小越好；用事件分组均值及覆盖率比较基线，同时报告概率可靠性、成本和未结算记录。不要只挑预测正确的新闻，也不要把每次更新都算作一个独立成功样本。

BLF 的公开论文也区分普通平均、logit 聚合及校准，并明确记录级交叉验证对未见问题的泛化可能过于乐观。本项目不应照搬其历史设置后宣称已解决这一问题。[论文聚合与校准附录](https://arxiv.org/html/2604.18576v5)。查阅时可在论文内搜索 “Combining independent trials” 和 “C.10 Calibration”。

## 5 对下一步开发的具体建议

- 先形成自有 `QuestionCompiler`：自然语言、窗口预设和领域识别进入模型结构化输出，再经过服务端确定性校验。生成的完整题目规则由用户可展开查看；只在主体歧义、口径冲突或无法生成有效规则时追问。
- 接通真实的 `search_web`、`fetch_page` 和至少一种固定来源适配器。我们的开发工具可以上网，不等于用户启动的 Node 服务也拥有网络搜索；运行期须配置实际提供商，并保存来源、取得时间和正文快照。
- 把角色定义扩展成“方法文档＋可调用工具＋输入／输出 Schema＋来源规则＋预算＋监听规则”；不要只新增十段提示词与十张人物卡。
- 定义一轮为“一个固定问题快照的一次有界研判”，内部可包含多个工具步骤、派工及小会。定时抓取不是每次都开会；先判断新颖性、相关性、来源可靠度和对关键争议的影响，只唤醒必要角色。重大矛盾或高影响事件才升级全体复核。
- 把监听保存为任务数据，包含查询／网站、角色、间隔范围、下次触发、上次水位、失败退避与到期条件。模型可建议计划，执行器限制可用来源、预算和频率，后台持久运行。
- 首版展示一个完整小闭环：一句话创建 → 预填规则 → 两个研究员自行找资料 → 一个核验研究员补查 → 发布二元概率 → 新资料触发局部更新 → 曲线新增一点 → 到期结算。这个闭环比继续增加手动配置页更有价值。

## 6 本次建议未证明的事项

本次是源码和论文调研，未实跑外部项目，也未复现论文结果。不能据此承诺“多 Agent 一定比单 Agent 准”、预测某位现实人物两天后的职位，或对股票涨跌给出当前真实概率。采用组件的下一步是小型可复现实验，并保留当前 Node／SQLite、版本与事件账本，避免以一次替换框架来掩盖仍未接通的取证与协作能力。
